## Phase 1 implementation decisions

- Keep wire version 1 and the 8 MiB tensor limit. Add `OVERLOADED=3` as an error status; existing successful requests retain their encoding.
- One sender owns request writes and one receiver owns reply reads. `infer_sync` waits on `infer_async`, so responses cannot be consumed by competing readers.
- Bound **all outstanding client requests**, including queued and executing requests. Reject excess submissions with an already-failed future rather than block the caller or grow memory without limit.
- Bound queued server tasks separately from the tasks currently executing. Default to one worker. Extra workers are a separate CPU-scaling experiment and require a thread-safe backend.
- Match responses by ID, allowing completion order to differ from submission order. A valid remote error fails only its request; malformed replies or a broken connection fail all unresolved futures.
- On close/disconnect, stop submission, discard queued work, interrupt socket I/O, settle futures, and join owned threads before closing descriptors. Already-running backend work is not forcibly cancelled.
- Preserve the existing per-transfer I/O timeout. An idle client receiver waits for pending work rather than timing out unused connections. A silent peer fails pending calls; `future.wait_for` does not cancel remote execution. Per-request execution deadlines/cancellation are separate future work.
- This phase continues to serve one active client connection at a time. Multiple outstanding requests are supported within that connection; fair multi-client scheduling is outside this milestone.

## Work order and external dependencies

Finish and validate phase 1 first, then build shared memory on the same request lifecycle, followed by ownership/pipelining. Instrument timings as those stages appear. Start comparative reporting only after the modes are correct. Keep the local C++ build independent of hardware SDKs.

Core ML, Qualcomm QNN/FastRPC integration, real NPU profiling, demo videos, and interview rehearsal are optional follow-ups. Actual hardware claims require the corresponding device/SDK and measurements. Native macOS and ARM64 results cannot be inferred from this Linux x86_64 environment; phase 5 obtained those results from native CI runners, as recorded in [the portability evidence](portability.md).

## Phase 2 decisions and the next boundary

SHM calls use fresh per-request regions, a 70-byte versioned descriptor, and an empty completion. The creator retains a mapping; the server validates and independently maps at admission, unlinks the name, and retains the mapping through queued/running work. Offsets, lengths, alignment, element counts, ownership, permissions, and actual size are checked. Creation reserves Linux backing storage; macOS PSXSHM size/mode differences are accounted for and were validated natively in phase 5. See [the shared-memory contract](shared-memory.md).

The per-request mode does not pool buffers. Phase 3 adds registered, retained mappings, slot generation/ownership tracking, fixed-capacity acquire/release, and preparation/execution overlap timestamps. Phase 4 must compare allocation-inclusive and pooled steady-state samples with repeated trials. Client SIGKILL before admission/registration can still orphan a name and requires identified-name recovery; no automatic orphan collector is claimed.

## Completion boundary

The six completion phases are delivered under the selected notes-only release
policy. Remaining work is explicitly outside that delivered scope: optional
profiling/longer performance studies, the diagnosed TSan runtime limitation,
hardware backends, fair multi-client scheduling, model/graph formats and owner
portfolio activities. Publishing a release/tag is a later explicit action. The
original 30-session plan contains historical checklists and optional exercises;
its unchecked boxes are not a claim that every exercise was executed.
